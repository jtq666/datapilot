# 简历五点工程设计与验收方案

> 本文件是 `data_platform` 的**可实施设计**，不是运行报告。主教材、关键源码讲解和面试表达见《数据智能平台项目学习与面试手册》（本地单独维护，未随仓库发布）。下文凡写“拟新增”均表示尚未实现；本文件不把未运行的模型评测写成实测。

## 0. 设计目标与现状

简历只保留五个彼此有区别的工作点：① Agent Harness 与原生 Tool Calling；② State 与 Trace；③ SQL 工具安全；④ Hybrid RAG；⑤ Agent Evaluation。有限恢复作为 State/Trace 的追问内容，不放在项目开场。整个项目共用一条请求链，而不是五个演示程序：

```text
React 问题 → FastAPI 鉴权与数据源检查 → 组装本轮模型/工具/提示词
→ AgentRunner 调用 Ollama/Qwen → ToolRegistry 校验并分发
├─ database_schema / query_database → 只读 SQLite
└─ search_knowledge → KnowledgeStore 的 BM25 + 向量 + RRF
→ 工具结果回注模型 → 继续调用或给出回答
→ RunStore 保存 Checkpoint 与摘要 Event → 页面获得回答和 run_id
```

当前源码已具备上述主链、40 题九表业务题集及自动评分脚本；新建的 32 题检索资产、19 份语料、Manifest、离线校验器和专用评测入口也已写入仓库，**尚未调用 Jina 运行**。仍缺的是异机两组结果的逐题原件、Agent 跨进程恢复的完整重建入口、统一故障注入题集和新 32 题的真实检索结果。设计或代码文件存在都不等于效果已经验收。

| 简历点 | 现有代码边界 | 达到可复核状态所需补齐 |
|---|---|---|
| Harness | `agents/runner.py`、`agents/tools.py`、`model_gateway/` 中的通用兼容 Provider 与 Ollama Provider | 协议矩阵测试与真实运行配置留档；不要仅凭文件名判断默认模型 |
| State / Trace | `runtime/store.py` 保存 Run、Event、Checkpoint；`AgentRunner.resume()` 已能接收构造好的模型和工具 | 运行绑定持久化、恢复 API/服务、跨进程及并发恢复用例 |
| SQL 安全 | `data_sources/sqlite_source.py` 的 SQLGlot + SQLite 只读/authorizer/限时限行 | 固定安全回归集、拒绝与执行错误分层记录；不声称生产沙箱 |
| Hybrid RAG | `knowledge/store.py` 实现 FTS5/BM25 + 余弦向量 + RRF；`search_knowledge` 可进入 Agent | 固定真实语料、32 题与逐题排名归档；不声称实时 Schema 自动同步 |
| Evaluation | `evaluation/run_agent_eval.py`、40 题与九表数据库 | 运行元数据、SQL/最终答案/人工复核分层报告，以及独立的检索、故障和续接报告 |

## 1. Harness：调用协议、工具合同与执行控制

**入口和职责。** `api/app.py::prepare_ask()` 按 workspace、数据源、可选知识库及 Agent/Skill 白名单组装工具；Provider 联系 Ollama/Qwen；`AgentRunner` 负责循环和 State（消息历史、`pending` 队列、轮次与答案）；`ToolRegistry` 负责 JSON Schema 参数校验及工具执行。模型只提出原生 `tool_calls`，不能直接拿数据库连接或绕过工具白名单。普通工具报错作为 `ToolResult` 回传。流式输出与有限恢复是这条主链的进阶能力；独立 Workflow 不属于 Agent Harness。

一次原生调用的数据合同是：模型回复包含 `tool_call_id + name + JSON arguments` → Registry 返回 `ok/data/error_code/message` → Runner 追加一条同 ID 的 `role=tool` 消息 → 下一轮由模型决定继续或停止。多个工具调用必须逐个推进 `next_tool` 并在每次结果后保存 Checkpoint。`max_turns` 限制模型回复轮数，不等于 SQL 调用次数；若以后要承诺查询上限或失败熔断，须新增独立计数和测试，不能把 `max_turns` 换个名称写到简历里。

**计划验收。** 确定性协议测试至少覆盖：无工具直接回答、一次/同轮多次调用、参数非 JSON、Schema 校验失败、未知工具、只读门控、工具执行错误与轮次耗尽。旧客户端提交 `protocol="react"` 应收到 422，不得静默按原生协议运行。真实 Ollama/Qwen 批量能力只按第 5 节的业务题结果报告，不由模拟 Provider 的单元测试推断。

## 2. State 与 Trace；中断恢复作为进阶追问

当前 RunStore 的三个表职责不同：`runs` 保存状态和版本，`events` 保存按序的模型/工具/状态摘要，`checkpoints` 保存可继续执行的 `messages/turns/pending/next_tool/answer`。Event 故意不保存完整参数、SQL、原始结果或密钥；要定位具体查询，应在受控权限下读 Checkpoint 或独立评测记录，不能把摘要 Event 称为全量 Trace。

**拟新增运行绑定 `agent_run_bindings`：** `run_id`（主键）、`workspace_id`、`source_name`、`knowledge_base_id`、`provider`、`model_name`、`tool_allowlist_json`、`agent_id`、`skill_id`、`config_version`、`created_at`。工具协议固定为原生 Tool Calling，无需为每次运行保存协议选择。它只存重建标识，不存 API Key 或原始工具结果。数据源路径继续通过 `identity.source_path(workspace_id, source_name)` 解析；知识库通过 `KnowledgeStore.ensure_scope()` 校验。创建 Run 时，绑定与初始状态必须协调保存；若绑定写入失败，不能留下一个可误恢复的孤儿 Run。

**拟新增恢复服务（不是现有 API）：** `POST /v1/workspaces/{workspace_id}/runs/{run_id}/resume`。还需为运行执行者增加受控租约/心跳，例如 `lease_owner`、`lease_expires_at`：硬崩溃不会触发 Python 的 `finally`，原 Run 可能仍是 `RUNNING`，现有 `resume()` 会拒绝它。新服务只能在原执行者租约已失效、且数据库版本检查成功后，把孤儿 `RUNNING` 标记为可恢复的 `FAILED`，再按“鉴权与 workspace 归属 → 读绑定与 Checkpoint → 校验数据源/知识库/模型配置仍可用 → 以原白名单重建 ToolRegistry → 构造 AgentRunner → 取得执行租约并带版本检查转移状态 → 调用现有 `resume()` → 返回状态和 run_id”处理。旧模型或配置不可用时明确报错，不静默换成另一模型/知识库；两个并发恢复请求至多一个取得租约和新版本，另一方不得继续工具执行。租约失效判断要考虑模型调用时长，执行者在每次工具前复核租约；运行资源在成功和异常路径都要关闭。

**边界。** 当前执行顺序是“工具完成 → 结果入 messages → Checkpoint”。如果进程恰好在前两步之间退出，恢复可能重复执行工具；当前工具只读，风险主要是重复耗时，并非 exactly-once。若未来接入发邮件、修改数据库等有副作用工具，必须另加工具级幂等键、执行结果账本和人工批准，不能仅靠 Checkpoint。

**计划验收。** 固定 6 组中断：模型调用前、模型返回后但工具未执行、工具执行后但未存盘、工具结果存盘后、硬崩溃后等待租约到期并由新进程恢复、两个请求并发抢恢复。逐组记录 `interrupt_triggered`、旧/新 Checkpoint 版本、租约归属、已执行工具次数、最终答案与错误；未实际中断不能算成功。只读工具使重复查询可容忍，但不能用此测试证明写操作不会重复。

## 3. SQL 工具安全与错误恢复

`query_database` 的信任边界固定为：**参数 JSON Schema → SQLGlot 单语句只读解析 → SQLite `mode=ro`/`query_only` → authorizer → 执行超时 → 结果行数上限 → 结构化 ToolResult**。`database_schema` 只给当前数据源的表和字段；模型不知道字段时可以先查 Schema，但 SQL 执行失败后模型是否修正由后续决策决定，程序不保证自动修好。

评测应把三种事分开：① 合法 SQL 的**结果**是否与 gold 表格匹配；② 危险 SQL 是否被拒绝；③ 错误真的触发后，Agent 是否收到结构化错误、改写查询并给出正确答案。建议冻结 12 组工具场景：8 组表/字段/语法/参数错误，4 组危险 SQL、重复 SQL、查询上限、连续失败；但当前项目**尚无**请求级 SQL 去重、查询上限、连续失败熔断的独立实现，这三项只能作为待实现/待验收的场景，不得写成现有能力。恢复结果分 `recovered`、`failed`、`not_triggered`、`configuration_error`；只有确实触发错误的组进入恢复率分母。

拟修改位置：`agents/runner.py` 添加独立的查询/失败计数时写入 Run State；`data_sources/agent_tools.py` 保持只读工具合同；`evaluation/` 用可控包装工具注入错误，**只在评测入口注入，不能让生产 API 接受“故障开关”**。安全 Event 记录工具名、错误码、耗时和受控的 SQL 摘要/哈希，不直接记录查询数据和敏感参数。验收中保留被拒绝用例和绕过尝试，但固定样例通过不代表对任意 SQL 的生产级安全证明。

## 4. Hybrid RAG：语料、检索、指标口径

当前真实链路只检索**已导入**的 TXT/MD 文档：`add_document()` 切块并为每块保存 FTS5 文本索引和 Embedding；`search()` 分别取 BM25 与余弦向量候选，再用 RRF 合并、截取前五；`search_knowledge` 以当前 workspace/知识库作用域把结果交给 Agent。实时数据库表结构另由 `database_schema` 读取。Jina Embeddings v3 是当前向量 Provider，Ollama/Qwen 是对话模型，二者职责不同。

**已冻结的新评测资产：** `evaluation/fixtures/retrieval_corpus_v1/` 保存九表 Schema、业务规则和指标说明共 19 份；`evaluation/datasets/retrieval_cases_v1.jsonl` 一行一题，字段为 `id/category/query/gold_filename/gold_reason`，共 32 题，分布为 12 指标、8 Schema、6 规则、6 组合。`retrieval_v1.manifest.json` 固定文件哈希与检索配置，`validate_retrieval_dataset.py` 离线检查数量、gold 与哈希。每个 gold 由业务语义在看搜索结果前指定；组合题只检查一个预定主来源，不能宣称全部必要证据均被找回。原异机题集若还在，应**原样归档**，不能拿本次新题集冒充旧 28/32 的输入。

**已写入、尚未运行的评测入口** `evaluation/run_retrieval_eval.py`：先校验 32 题和 gold 文件 → 固定 Embedding/切块/top_k=5/candidate_k=16 → 用独立临时 KnowledgeStore 导入文档 → 每题保存前五的 `filename/ordinal/chunk_id/keyword_rank/vector_rank` 与 gold 排名 → 输出 Recall@5、MRR@5、语料/题集哈希与配置。主手册 7.6.2 解释关键代码和命令。现有 16 题合成基准只检查管线连通，不可替代新题集的真实运行分数。若对比 BM25-only、vector-only 与 RRF，三种模式必须在同一语料和题上各自真正排序；融合结果中的 `keyword_rank` 不能直接当单路实验的 Recall。

项目目前没有运行时权威 JSON 指标目录。若未来需要统一净收入等计算口径，应另建按数据源版本化的 JSON 定义及校验模块，让 RAG 只负责检索说明，不能让检索片段改写权威公式；这不是当前五点简历已经完成的能力。

## 5. Agent Evaluation：固定输入、分层计分与证据

业务线沿用 `orders_eval_v2.db`、`business_cases_v2.jsonl`、Manifest 的九表 40 题。`run_agent_eval.py` 每题检查：① 至少一份 SQL 工具表格与 gold 匹配；② 最终 JSON 的 `columns/rows` 与 gold 匹配；③ Run 成功且 `answer` 非空；三者都成立才有 `task_success=true`。这只证明脚本口径的结构化任务通过，中文结论、遗漏条件和证据引用仍需人工复核。当前 40 题脚本只注册 SQL 工具，因此其得分**不是**“开启 RAG 后的端到端提升”。

检索线按第 4 节的单 gold 口径计分：gold 文件进入前五为 1，否则 0，Recall@5 是命中题数/32；MRR@5 是各题首个 gold 排名倒数之和/32。两条线不能相加。作者提供的异机汇总为业务 `34/40（85%）` 和检索 `28/32（87.5%）`；原始逐题文件当前不在仓库，不能虚构哪 6 道、哪 4 道失败，也不能从两个数字推出 RAG 带来多少提升。

**每次正式运行的固定包：**

```text
evaluation/results/<run_id>/
  manifest.json           # 日期、代码版本、题集/数据库/语料哈希、模型与参数、评分版本
  business_cases.jsonl    # 逐题工具结果、最终答案、三项自动评分；不含密钥
  retrieval_cases.jsonl   # 逐题 gold、前五来源、排名和命中
  human_review.jsonl      # 人工核验的结论、理由、复核人/时间
  summary.json            # 分母、分子、分类失败数、适用范围
```

没有参加某条评测线时，不创建伪造的空“成功记录”，而是在 Manifest 标明 `not_run`。现有评测脚本没有导出完整模型消息或 Run Event；若要用于逐步审计，需在评测入口增加**脱敏的受控轨迹导出**，不能因正常 API 的 RunStore 有事件就声称现有 JSONL 已包含完整 Trace。运行步骤：冻结输入/规则 → 数据集校验 → 1 题冒烟 → 全量运行 → 核对 ID/分母 → 自动计分 → 人工复核 → 锁定报告。原件找不到时只能新跑并标新日期；不为追平旧数字改 gold、删失败题或拼接不同配置的批次。

若将来要证明 Hybrid RAG 对业务题有**增益**，先让同一 Agent 业务评测入口实际注册/不注册检索工具，并在同一冻结子集、同一模型和参数下做成对对照；分别报告两组任务正确数及差值。目前没有这组实验，简历只分别写 85% 与 87.5%。
